# Reflections: TRIXC ONNX → Executable Pipeline

## Core Insight

**The compiler is a template engine, not a code generator.**

Looking at the pattern:
- The shapes are already written (onnx_shapes.h)
- The execution order is already determined (ONNX graph)
- The weights are already extracted (onnx2trix.py)

The "compiler" just fills in a template:
```
[WEIGHT DECLARATIONS]
[INIT FUNCTION]
[FORWARD FUNCTION with shape calls in order]
[CLEANUP FUNCTION]
[MAIN with I/O]
```

This is simpler than I thought. It's string formatting, not compilation.

---

## Resolved Tensions

### Tension 1: Python vs C compiler → Python

Python already:
- Parses ONNX (onnx library)
- Produces JSON (built-in)
- Has the onnx2trix.py infrastructure

Adding C emission is just adding string templates. No reason to switch languages.

### Tension 2: Embedded vs external weights → Embedded (with escape hatch)

For models < 10MB of weights, embedding is fine. A 10MB C array compiles in seconds.

For larger models, add `--external-weights` flag later. But v1 embeds everything.

### Tension 3: alloca vs malloc → alloca with size check

```c
#define TRIX_STACK_LIMIT (1024 * 1024)  // 1MB

void* buf = (size < TRIX_STACK_LIMIT) ? alloca(size) : malloc(size);
```

Simple heuristic. Stack for small, heap for large.

### Tension 4: Dynamic vs fixed shapes → Fixed with named constants

```c
#define MODEL_BATCH 1
#define MODEL_SEQ_LEN 128
#define MODEL_D_MODEL 768
```

User can edit these and recompile. Dynamic shapes are a v2 feature.

### Tension 5: Broadcasting → Error on mismatch

Broadcasting is complex (NumPy rules). For v1, require exact dimension match.

The converter can detect this and error early:
```
Error: Shape mismatch at Add_3: [1, 768] vs [768].
Broadcasting not supported. Use explicit Expand.
```

## What Would This Look Like If It Were Easy?

One function call:
```python
def generate_c_code(trix: Dict) -> str:
    return TEMPLATE.format(
        weights=emit_weights(trix["weights"]),
        init=emit_init(trix),
        forward=emit_forward(trix["shapes"]),
        main=emit_main(trix["inputs"], trix["outputs"])
    )
```

Each `emit_*` function is straightforward string building.

## The Forward Function Pattern

For each shape in order:
```c
// Shape 0: MatMul (input → t0)
trix_onnx_matmul(input, w_0, t0, M, N, K);

// Shape 1: Add (t0 + bias → t0, in-place)
trix_onnx_add(t0, b_0, t0, N);

// Shape 2: GELU (t0 → t1)
for (int i = 0; i < N; i++) t1[i] = trix_onnx_gelu(t0[i]);

// Shape 3: LayerNorm (t1 → output)
trix_onnx_layer_norm(t1, ln_w, ln_b, output, N, 1e-5f);
```

The complexity is:
1. Mapping shape inputs/outputs to buffer names
2. Computing buffer sizes from dimensions
3. Matching the right shape function signature

---

## Buffer Naming Strategy

ONNX uses string names: `"input_0"`, `"MatMul_output_0"`, etc.

Strategy:
1. Map each unique tensor name to a buffer: `t0`, `t1`, `t2`, ...
2. Inputs map to function parameters
3. Outputs map to output parameters
4. Weights map to model struct fields
5. Intermediates are local buffers

## The Generated File Structure

```c
/* model.c - Generated by trixc from model.onnx */

#include "trixc/onnx_shapes.h"
#include <stdlib.h>
#include <stdio.h>

/* ═══ Configuration ═══ */
#define BATCH_SIZE 1
#define SEQ_LEN 128
#define D_MODEL 768

/* ═══ Weights ═══ */
static const float W_0[768 * 3072] = { ... };
static const float B_0[3072] = { ... };
// ...

/* ═══ Forward Pass ═══ */
void model_forward(const float* input, float* output) {
    float* t0 = alloca(3072 * sizeof(float));
    float* t1 = alloca(768 * sizeof(float));

    // MatMul
    trix_onnx_matmul(input, W_0, t0, 1, 3072, 768);

    // Add bias
    trix_onnx_add(t0, B_0, t0, 3072);

    // GELU
    for (int i = 0; i < 3072; i++) t0[i] = trix_onnx_gelu(t0[i]);

    // Project down
    trix_onnx_matmul(t0, W_1, output, 1, 768, 3072);
}

/* ═══ Main ═══ */
int main(int argc, char** argv) {
    float input[768];
    float output[768];

    // Read input from stdin or file
    fread(input, sizeof(float), 768, stdin);

    // Run model
    model_forward(input, output);

    // Write output
    fwrite(output, sizeof(float), 768, stdout);

    return 0;
}
```

## What I Now Understand

1. **The compiler is simple** - it's template-based string generation
2. **The hard work is done** - shapes exist, graph is sorted
3. **v1 can be restrictive** - fixed shapes, embedded weights, no broadcast
4. **Extend onnx2trix.py** - add `--emit-c` flag
5. **Output is single .c file** - self-contained, easy to compile

This isn't code generation. It's transcription.
